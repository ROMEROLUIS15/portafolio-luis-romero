# Requirements Document

## Introduction

Luis Romero's portfolio (AI Engineer / Backend Developer) requires an embedded conversational agent that lets recruiters and visitors ask natural-language questions about his experience, projects, and skills, receiving contextual responses backed by real data.

The agent is implemented as a **floating chat widget** (fixed bubble, bottom-right corner) present on both portfolio versions (EN at `/index.html`, ES at `/spanish/index.html`). The backend is a **Supabase Edge Function** (Deno/TypeScript) that runs a RAG pipeline: retrieves relevant chunks from `pgvector`, builds an enriched prompt, and sends it to **Groq** (`llama3-70b-8192`) for response generation. Embeddings are generated using the OpenAI `text-embedding-ada-002` model (1536 dimensions). Data sources are the CVs in PDF (EN and ES) and `cronix-stats.json`. The endpoint is public with anti-abuse protection via **IP-based rate limiting** (10 req/min) and ephemeral session tokens. If the endpoint fails, the widget shows a static fallback message.

The demonstrable purpose is to showcase exactly what Luis knows how to build: a RAG agent with a real stack (Supabase + pgvector + OpenAI embeddings + Groq) embedded in production.

## Glossary

- **Chat_Widget**: The embedded UI component in the portfolio, implemented in vanilla HTML/CSS/JS (IIFE in `assets/js/chat-widget.js`), that renders the chat bubble and conversation panel.
- **Edge_Function**: The Supabase serverless function running on Deno/TypeScript (`supabase/functions/chat/index.ts`) that acts as the agent's backend.
- **RAG_Pipeline**: The Retrieval-Augmented Generation pipeline that retrieves relevant context chunks from the Vector_Store and injects them into the prompt sent to the LLM.
- **Vector_Store**: The `documents` table in Supabase PostgreSQL with the `pgvector` extension, storing embeddings of the CVs and Cronix data as 1536-dimensional vectors. Document metadata (`source`, `lang`, `chunk_index`, `created_at`) is stored in a `metadata` JSONB column.
- **LLM**: The large language model provided by Groq (`llama3-70b-8192`) that generates the agent's responses.
- **Session_Token**: An ephemeral UUID (RFC 4122 v4) generated by the Chat_Widget at the start of each browser session, stored in `sessionStorage` under the key `"cw_session_token"`, and used to group messages and apply session-level tracking.
- **Rate_Limiter**: The mechanism inside the Edge_Function that controls request frequency per IP address using the `rate_limits` table in Supabase.
- **Knowledge_Base**: The set of data sources ingested into the Vector_Store: CVs in PDF (EN and ES) and `cronix-stats.json`.
- **Ingestion_Script**: The Deno script (`scripts/ingest.ts`) that processes Knowledge_Base sources, generates embeddings using the OpenAI `text-embedding-ada-002` model, and inserts them into the Vector_Store.
- **Visitor**: Any person accessing the portfolio (recruiter, potential collaborator, or other visitor).
- **Similarity_Threshold**: The minimum cosine similarity score (0.70) required for a retrieved chunk to be considered relevant context. Applied by the Edge_Function after retrieval, not inside `match_documents`.
- **System_Prompt**: The fixed instruction injected at the start of each LLM request, defining the agent's persona, scope, and language.
- **match_documents**: The PostgreSQL RPC function that accepts a query embedding, a target language, and a match count, and returns the top N chunks ordered first by language match (same language prioritized) and then by ascending cosine distance (descending similarity).

## Requirements

### Requirement 1: Floating Chat Widget

**User Story:** As a portfolio visitor, I want to see a floating chat button in the bottom-right corner of the page, so that I can start a conversation with the agent whenever I want without it interfering with the main content.

#### Acceptance Criteria

1. THE Chat_Widget SHALL render a fixed circular button (56×56 px) at `position: fixed; bottom: 24px; right: 24px` on both portfolio versions (EN at `/index.html` and ES at `/spanish/index.html`), visible on viewport widths from 320 px upward.
2. WHEN a Visitor clicks the Chat_Widget button while the panel is closed, THE Chat_Widget SHALL expand the conversation panel to at least 340×480 px without reloading the page or disrupting the portfolio's scroll position.
3. WHEN the conversation panel is open and the Visitor clicks the close button inside the panel, THE Chat_Widget SHALL collapse the panel without clearing the message history accumulated since the current page load.
4. WHEN the conversation panel is open and the Visitor presses the `Escape` key, THE Chat_Widget SHALL collapse the panel without clearing the message history accumulated since the current page load.
5. WHILE the conversation panel is open, THE Chat_Widget SHALL display the session's message history in a scrollable container with its own internal scroll, and SHALL automatically scroll to the most recent message each time a new message is added.
6. WHILE the Edge_Function is processing a request, THE Chat_Widget SHALL display a typing indicator (three animated dots) inside the conversation panel, and SHALL disable the message input field and send button until the response is received or an error is returned; IF no response is received within 8 seconds from the time the request was sent, THE Chat_Widget SHALL cancel the in-flight request using `AbortController` and display the localized service-unavailable fallback message (defined in Requirement 5, AC3) and SHALL re-enable the message input field and send button.
7. THE Chat_Widget SHALL apply the CSS custom properties `--accent`, `--bg-card`, `--bg-primary`, `--bg-secondary`, `--text-primary`, `--text-secondary`, `--text-muted`, `--border`, and `--accent-light` defined in `assets/css/style.css` to integrate visually with both the dark and light themes of the portfolio.
8. WHERE the portfolio version has `<html lang="es">`, THE Chat_Widget SHALL display all interface labels, placeholder text, error messages, and button tooltips in Spanish; WHERE the portfolio version has `<html lang="en">`, THE Chat_Widget SHALL display all interface labels, placeholder text, error messages, and button tooltips in English.
9. THE Chat_Widget SHALL assign `role="dialog"` and a localized `aria-label` to the conversation panel element, and SHALL assign a localized `aria-label` and `aria-expanded` (set to `"true"` when open, `"false"` when closed) to the open/close bubble button, so that screen readers can announce the widget's purpose and state.
10. WHEN the conversation panel opens, THE Chat_Widget SHALL move keyboard focus to the message input field within 250 ms; WHEN the panel closes, THE Chat_Widget SHALL return keyboard focus to the chat bubble button.
11. WHEN the conversation panel is open and a Visitor clicks outside both the panel and the bubble button, THE Chat_Widget SHALL collapse the panel without clearing the message history.

### Requirement 2: Knowledge Base Ingestion

**User Story:** As the portfolio administrator (Luis), I want to ingest the CVs in PDF and the Cronix data into the Vector Store, so that the agent has real and up-to-date context when answering questions.

#### Acceptance Criteria

1. THE Ingestion_Script SHALL extract text from `assets/images/LuisRomero_AIEngineer-Backend_2026_EN.pdf` and `assets/images/LuisRomero_AIEngineer-Backend_2026_ES.pdf`, splitting each document into text chunks where each chunk contains between 200 and 500 estimated tokens (approximated at 4 characters per token, ~1.25 words per token) with a 50-token overlap between consecutive chunks; each chunk SHALL contain at least one non-whitespace character.
2. THE Ingestion_Script SHALL process `cronix-stats.json` by: (a) converting each top-level scalar field (type string, number, or boolean) into a plain-text string of the form `"Cronix <key>: <value>"`; (b) converting each object-valued top-level field (excluding the `changelog` array) into a plain-text string of the form `"Cronix <key>: <JSON-serialized value>"`; and (c) converting each entry in the `changelog` array into a plain-text string of the form `"Cronix changelog entry — <key1>: <val1>, <key2>: <val2>, ..."`. The resulting plain-text strings SHALL be joined and chunked using the same algorithm as AC1. The `cronix-stats.json` source SHALL be tagged with `lang = "en"`.
3. WHEN the Ingestion_Script processes a text chunk, THE Ingestion_Script SHALL generate a 1536-dimensional embedding vector using the OpenAI `text-embedding-ada-002` model and insert a row into the Vector_Store with the fields: `content` (text), `embedding` (vector(1536)), and a `metadata` JSONB object containing: `source` (filename string, e.g., `"LuisRomero_AIEngineer-Backend_2026_EN.pdf"`), `lang` (`"en"` or `"es"`), `chunk_index` (non-negative integer, zero-based, representing the chunk's position in the source), and `created_at` (UTC ISO-8601 timestamp string captured at the start of the ingestion run).
4. WHEN the Ingestion_Script is executed and the Vector_Store already contains rows for the same `source` value in the `metadata` column, THE Ingestion_Script SHALL insert new rows for all chunks of that source without deleting or updating existing rows (additive ingestion). Operators who want a clean re-ingestion SHALL manually delete existing rows for that source before re-running the script.
5. IF the Ingestion_Script cannot read a source file at its expected path, THEN THE Ingestion_Script SHALL emit a `console.error` message that includes the missing file path, skip that file, and continue processing all remaining source files without terminating.
6. IF the OpenAI embeddings API returns an HTTP error for a batch of chunks, THEN THE Ingestion_Script SHALL retry that batch up to 3 times with exponential back-off starting at 1000 ms and doubling on each retry (1000 ms, 2000 ms, 4000 ms); if all retries fail, THE Ingestion_Script SHALL skip the batch, log the number of skipped chunks via `console.warn`, and continue processing remaining batches.
7. THE Vector_Store SHALL maintain an HNSW index on the `embedding` column using cosine distance operator `vector_cosine_ops`, with `m = 16` and `ef_construction = 64`, such that a cosine similarity search over up to 10,000 vectors returning the top-5 nearest neighbors completes in under 500 ms measured from when the `match_documents` RPC call is issued to when results are received by the Edge_Function.
8. IF the Ingestion_Script is invoked without any of the required environment variables `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, or `OPENAI_API_KEY`, THEN THE Ingestion_Script SHALL emit a `console.error` message identifying each missing variable by name and SHALL exit with a non-zero status code (`Deno.exit(1)`) without attempting to process any source files.

### Requirement 3: RAG Pipeline and Response Generation

**User Story:** As a visitor, I want to send a question to the agent and receive a precise, contextualized response about Luis Romero's experience in under 5 seconds, so that I can quickly evaluate whether his profile fits my needs.

#### Acceptance Criteria

1. WHEN a Visitor sends a message, THE Edge_Function SHALL: (a) generate a 1536-dimensional embedding of the message text using the OpenAI `text-embedding-ada-002` model; (b) call the `match_documents` RPC function with the query embedding, the `lang` value from the request body, and `match_count = 5`; and (c) receive back up to 5 chunks ordered first by language match (same `lang` value prioritized) and then by ascending cosine distance (i.e., descending cosine similarity).
2. WHEN the Edge_Function receives the chunks from `match_documents`, THE Edge_Function SHALL compute the maximum cosine similarity score across all returned chunks; IF that maximum is below 0.70 OR if `match_documents` returns zero chunks, THEN THE Edge_Function SHALL return HTTP 200 with JSON body `{ "answer": "<localized out-of-scope message>", "sources": [] }` without invoking the LLM. The out-of-scope message SHALL be: in English — "I don't have enough context to answer that question. You can reach Luis directly at lueduar15@gmail.com."; in Spanish — "No tengo suficiente contexto para responder esa pregunta. Puedes contactar a Luis directamente en lueduar15@gmail.com."
3. THE Edge_Function SHALL include a System_Prompt in every LLM request that: (a) identifies the agent as an AI assistant for Luis Romero's portfolio; (b) instructs the LLM to answer only using the provided context chunks; (c) instructs the LLM to state that the information is not available if the context is insufficient; (d) instructs the LLM to never invent data, dates, technologies, projects, or metrics not present in the context; and (e) specifies the response language (English or Spanish) matching the `lang` parameter.
4. WHEN the LLM generates a response, THE Edge_Function SHALL return HTTP 200 with JSON body `{ "answer": string, "sources": string[] }`, where `sources` is a deduplicated array of the `source` metadata values from the retrieved chunks, within a total end-to-end time (request receipt to response sent) of under 5 seconds under normal operating conditions.
5. THE Edge_Function SHALL invoke the LLM using the Groq API (`https://api.groq.com/openai/v1/chat/completions`), the model identifier `llama3-70b-8192`, `temperature: 0.3`, and `max_tokens: 512`.
6. THE Edge_Function SHALL return responses as a single complete JSON body (non-streaming), with `Content-Type: application/json`; server-sent event (SSE) streaming SHALL NOT be used.
7. IF the Groq API call, the OpenAI embeddings API call, or the `match_documents` RPC call throws an error or returns an HTTP error status during a request, THEN THE Edge_Function SHALL return HTTP 500 with JSON body `{ "error": "internal_error" }` and SHALL emit a `console.error` log entry with the error details.

### Requirement 4: Anti-Abuse Protection and Rate Limiting

**User Story:** As the portfolio owner (Luis), I want to protect the agent endpoint against abusive use, so that I can avoid excessive API costs and guarantee availability for legitimate visitors.

#### Acceptance Criteria

1. THE Rate_Limiter SHALL enforce a maximum of 10 requests per IP address within a 60-second sliding window by recording the IP address, request count, and window start time in the `rate_limits` table; WHEN a request arrives and the elapsed time since `window_start` exceeds 60 seconds, THE Rate_Limiter SHALL reset the count to 1 and update `window_start` to the current time.
2. IF an IP address has made 10 or more requests within the current 60-second window, THEN THE Edge_Function SHALL return HTTP 429 with JSON body `{ "error": "rate_limit_exceeded", "retry_after": <integer — ceiling of remaining seconds in the window> }` without executing the RAG_Pipeline.
3. IF the `rate_limits` table query fails for any reason, THEN THE Edge_Function SHALL allow the request to proceed (fail-open behavior) and emit a `console.warn` log entry with the error details.
4. THE Edge_Function SHALL validate that every request includes the `X-Session-Token` header containing a string that matches the UUID v4 format (regex: `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, case-insensitive); IF the header is absent or the value does not match the UUID v4 format, THEN THE Edge_Function SHALL return HTTP 400 with JSON body `{ "error": "invalid_session_token" }` without executing the RAG_Pipeline.
5. THE Edge_Function SHALL validate that the request body contains a `message` field of type `string` with a length between 1 and 500 characters (inclusive); IF the request body is not valid JSON, the `message` field is absent, the `message` field is not a string, or the `message` field's length is outside the range 1–500, THEN THE Edge_Function SHALL return HTTP 422 with JSON body `{ "error": "invalid_message", "max_length": 500 }` without executing the RAG_Pipeline.
6. WHEN the Edge_Function receives an HTTP OPTIONS preflight request, THE Edge_Function SHALL return status 204 with headers `Access-Control-Allow-Methods: POST, OPTIONS` and `Access-Control-Allow-Headers: Content-Type, X-Session-Token, Authorization`; IF the request `Origin` header matches an entry in the `ALLOWED_ORIGINS` environment variable (comma-separated allowlist) or is a localhost origin (any port on `http://localhost` or `http://127.0.0.1`), THEN THE Edge_Function SHALL also include `Access-Control-Allow-Origin` set to that origin value; OTHERWISE the header SHALL be omitted.
7. IF a non-OPTIONS request arrives from an origin not in the allowlist described in AC6, THEN THE Edge_Function SHALL return HTTP 403 with JSON body `{ "error": "forbidden" }` without executing the RAG_Pipeline.

### Requirement 5: Widget Fallback Behavior

**User Story:** As a visitor, I want the chat widget to remain usable even when the backend fails, so that the portfolio experience is not broken by an agent error.

#### Acceptance Criteria

1. IF the Edge_Function returns HTTP status 500 or higher, THEN THE Chat_Widget SHALL wait 1 second after receiving the error response and retry the same request; IF that retry also returns HTTP 500 or higher, THE Chat_Widget SHALL wait 2 seconds after receiving the second error response and retry once more; IF the third attempt also returns HTTP 500 or higher, THEN THE Chat_Widget SHALL display the localized service-unavailable fallback message (defined in AC3) as an error message in the conversation panel and SHALL re-enable the message input field and send button.
2. IF a request to the Edge_Function does not receive a response within 8 seconds from the time the request was sent, THEN THE Chat_Widget SHALL cancel the request using `AbortController`, display the localized service-unavailable fallback message (defined in AC3) as an error message in the conversation panel, and SHALL re-enable the message input field and send button without retrying.
3. THE Chat_Widget SHALL display the following localized service-unavailable fallback message in error states defined in AC1 and AC2: in English — "Sorry, the agent is currently unavailable. You can reach me at lueduar15@gmail.com"; in Spanish — "Lo siento, el agente no está disponible ahora mismo. Puedes contactarme en lueduar15@gmail.com".
4. IF the Edge_Function returns HTTP 429, THEN THE Chat_Widget SHALL display a localized message that includes the number of seconds from the `retry_after` field of the response body (e.g., in English: "Too many requests. Please wait {N}s before sending another message.") and SHALL disable the message input field and send button for exactly that number of seconds before re-enabling them and returning keyboard focus to the input field.
5. IF the Edge_Function returns HTTP 400 or HTTP 422, THEN THE Chat_Widget SHALL display a localized validation error message in the conversation panel as an error-styled system message, SHALL re-enable the message input field and send button, and SHALL log the full response body to `console.error`; the user-visible error message SHALL NOT contain HTTP status codes, JSON field names, or stack traces.
6. WHILE the Chat_Widget is in any error or fallback state described in AC1–AC5, THE Chat_Widget SHALL continue displaying the full message history of the current session above the error message.

### Requirement 6: Bilingual Agent Support

**User Story:** As a visitor, I want the agent to respond in the language of the portfolio version I am viewing, so that my experience is coherent with the rest of the site.

#### Acceptance Criteria

1. WHEN a Visitor sends a message from the Spanish version (`/spanish/index.html`, where `<html lang="es">`), THE Chat_Widget SHALL include `"lang": "es"` in the JSON body of the request sent to the Edge_Function.
2. WHEN a Visitor sends a message from the English version (`/index.html`, where `<html lang="en">`), THE Chat_Widget SHALL include `"lang": "en"` in the JSON body of the request sent to the Edge_Function.
3. WHEN the Chat_Widget sends a request, THE Chat_Widget SHALL derive the `lang` parameter value by reading the `lang` attribute of the `<html>` element (`document.documentElement.lang`) at the exact moment the request is sent, comparing the value case-insensitively.
4. IF the `<html>` element has no `lang` attribute, or the attribute value is not `"es"` (case-insensitive) at the time the message is sent, THEN THE Chat_Widget SHALL use `"en"` as the `lang` parameter value.
5. WHEN the Edge_Function receives a request with `"lang": "es"`, THE Edge_Function SHALL include a Spanish-language instruction in the System_Prompt instructing the LLM to respond in Spanish, and SHALL pass `query_lang = 'es'` to the `match_documents` RPC function.
6. WHEN the Edge_Function receives a request with `"lang": "en"`, THE Edge_Function SHALL include an English-language instruction in the System_Prompt instructing the LLM to respond in English, and SHALL pass `query_lang = 'en'` to the `match_documents` RPC function.
7. IF the Edge_Function receives a request body with a `lang` field whose value is not `"es"` or `"en"`, or with no `lang` field, THEN THE Edge_Function SHALL default to `"en"` for both the System_Prompt language instruction and the `query_lang` argument passed to `match_documents`.

### Requirement 7: Suggested Questions and Onboarding Experience

**User Story:** As a recruiter visiting the portfolio for the first time, I want to see example questions I can ask the agent, so that I quickly understand what kind of information I can obtain.

#### Acceptance Criteria

1. WHEN the Chat_Widget panel is opened for the first time in a browser session (i.e., `state.messages` is empty), THE Chat_Widget SHALL display a welcome message followed by exactly 3 suggested question buttons in the language corresponding to the active portfolio version. The welcome message SHALL be: in English — "Hi! I'm Luis's AI assistant. I can answer questions about his experience, projects, and skills. What would you like to know?"; in Spanish — "¡Hola! Soy el asistente IA de Luis. Puedo responder preguntas sobre su experiencia, proyectos y habilidades. ¿Qué te gustaría saber?"
2. THE Chat_Widget SHALL display the following suggested question texts when `lang` is `"es"`: "¿Qué experiencia tiene Luis con LangGraph?", "¿Cuáles son las métricas reales de Cronix?", "¿Qué stack usa Luis para sistemas anti-alucinación?".
3. THE Chat_Widget SHALL display the following suggested question texts when `lang` is `"en"`: "What is Luis's experience with LangGraph?", "What are Cronix's real production metrics?", "What stack does Luis use for anti-hallucination systems?".
4. WHEN a Visitor clicks a suggested question button, THE Chat_Widget SHALL display the button's question text as a Visitor message in the conversation panel and SHALL immediately submit that text as the `message` field in the request body sent to the Edge_Function.
5. WHEN the current session already contains at least one Visitor message and at least one agent response (i.e., `state.hasHadExchange` is `true`), THE Chat_Widget SHALL not render the suggested question buttons, regardless of how many times the panel is closed and reopened during the same session.
6. WHEN the Chat_Widget panel is closed and reopened within the same browser session and the suggested question buttons have been hidden per AC5, THE Chat_Widget SHALL not re-display the suggested question buttons.

### Requirement 8: Observability and Logging

**User Story:** As the portfolio owner (Luis), I want to record agent interactions in Supabase, so that I can monitor usage, detect frequent questions, and demonstrate the system's operation to future clients.

#### Acceptance Criteria

1. WHEN the Edge_Function returns HTTP 200 to the Chat_Widget (whether a successful LLM response or an out-of-scope fallback), THE Edge_Function SHALL insert a row into the `chat_logs` table with the following fields: `session_token` (UUID string from the `X-Session-Token` header), `lang` (string, `"en"` or `"es"`), `message_hash` (SHA-256 hex digest of the raw user message string), `chunks_retrieved` (integer — the total number of chunks returned by `match_documents` that proceeded to the LLM call, or 0 if the similarity threshold was not met or no chunks were returned), `response_time_ms` (integer — milliseconds elapsed from request receipt to the moment the HTTP response is sent), and `created_at` (auto-generated UTC timestamp via `DEFAULT now()`).
2. THE Edge_Function SHALL store the user message exclusively as its SHA-256 hex digest (64-character lowercase hexadecimal string) in the `message_hash` field and SHALL never write the plaintext message text to any Supabase table, any log line, or any other storage.
3. THE Edge_Function SHALL perform the `chat_logs` INSERT as a fire-and-forget asynchronous operation (initiated with `.then()` and not awaited on the response path) so that a slow or failing database write does not block or delay the HTTP response to the Chat_Widget.
4. IF the INSERT into `chat_logs` fails for any reason, THEN THE Edge_Function SHALL emit a `console.warn` log entry containing the error details and SHALL continue without any impact on the Visitor's experience.
5. THE `chat_logs` table SHALL be protected by Row Level Security (RLS) in Supabase, permitting INSERT operations only when authenticated with the service role key, and denying all SELECT, UPDATE, and DELETE operations from the `anon` role or any role other than `service_role`.
6. THE `chat_logs` table schema SHALL include the following columns: `id` (bigserial primary key), `session_token` (uuid not null), `lang` (text not null, constrained to `'es'` or `'en'` via a CHECK constraint), `message_hash` (text not null), `chunks_retrieved` (int not null), `response_time_ms` (int not null), and `created_at` (timestamptz not null, default `now()`).

### Requirement 9: Session Token Lifecycle

**User Story:** As the portfolio owner (Luis), I want the chat widget to manage session tokens transparently, so that each browser session is consistently identified without requiring the visitor to authenticate.

#### Acceptance Criteria

1. WHEN the Chat_Widget JavaScript is first executed in a browser session and `sessionStorage` does not contain the key `"cw_session_token"`, THE Chat_Widget SHALL generate a new UUID v4 string matching the format `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` using `crypto.getRandomValues`, store it under `"cw_session_token"` in `sessionStorage`, and use it for all subsequent requests in that session.
2. WHEN the Chat_Widget JavaScript is first executed in a browser session and `sessionStorage` already contains a string under the key `"cw_session_token"`, THE Chat_Widget SHALL reuse that stored value without generating a new UUID, preserving session continuity across panel open/close actions within the same page load.
3. THE Chat_Widget SHALL include the Session_Token as the value of the `X-Session-Token` HTTP header in every request sent to the Edge_Function.
4. THE Chat_Widget SHALL store the Session_Token exclusively in `sessionStorage` and SHALL NOT store it in `localStorage`, any cookie, or any other persistent storage, ensuring that the token does not persist across browser tab closures or separate browser sessions.

### Requirement 10: Accessibility and Mobile Responsiveness

**User Story:** As a visitor using a mobile device or assistive technology, I want the chat widget to be fully usable, so that I can access the same conversational experience regardless of my device or access method.

#### Acceptance Criteria

1. THE Chat_Widget SHALL render on viewport widths from 320 px to 2560 px such that the conversation panel does not overflow the visible viewport horizontally or vertically at any supported screen size.
2. WHEN the viewport width is less than 480 px, THE Chat_Widget SHALL expand the conversation panel to fill the full viewport width (`width: 100%`, `left: 0`, `right: 0`) with rounded top corners and no bottom margin, and SHALL occupy at least 60% of the viewport height (`min-height: 60vh`), rather than using the desktop fixed-size dimensions.
3. THE Chat_Widget bubble button and all interactive elements within the conversation panel (including the send button, suggested question buttons, and the close button) SHALL have a minimum tap/click target size of 44×44 px to comply with WCAG 2.2 success criterion 2.5.8.
4. THE Chat_Widget SHALL not render any text content with a foreground-to-background color contrast ratio below 4.5:1, using the CSS custom property values for `--text-primary`, `--text-secondary`, `--text-muted`, `--bg-card`, `--bg-primary`, and `--bg-secondary` defined in `assets/css/style.css`.
5. WHEN the Chat_Widget conversation panel is open, THE Chat_Widget SHALL trap keyboard focus within the panel such that pressing Tab cycles only through focusable elements inside the panel, and pressing Shift+Tab cycles in reverse order, preventing focus from reaching page elements behind the panel until the panel is closed.
